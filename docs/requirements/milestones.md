# Milestones

The milestone ladder for the product described in [product-requirements.md](product-requirements.md), built with the stack in [technical-requirements.md](technical-requirements.md). Each milestone is delivered as one Spec Kit feature.

The ladder follows a "walking skeleton" approach: first ship an empty skeleton to the internet, then grow it with vertical slices. Each step ends with a working, testable and meaningful result.

**Delivered milestones** are short summaries of what the product does after them. Their specification in [`specs/`](../../specs/) is the source of truth for details, and the summary is updated only if the product behaviour changes. **Upcoming milestones** hold the full scope, refined until every detail is clear, and are the input for `speckit-specify`.

## Delivered

1. **Hello World locally.** _Spec:_ [001-hello-world-page](../../specs/001-hello-world-page/spec.md)
   - The application runs on a developer's machine and serves one server-rendered home page with the application name and a short description of its purpose.
   - The page is readable on desktop and phone-width screens. Unknown addresses show a friendly "not found" page.
   - A developer can set up, run and test the application by following the README.

2. **Deploy Hello World to the internet + CI/CD.** _Spec:_ [002-public-deploy-cicd](../../specs/002-public-deploy-cicd/spec.md)
   - The home page from milestone 1, unchanged, is available to anyone at a public HTTPS address.
   - Every pull request is checked automatically (tests, code style, formatting) and cannot be merged while a check fails.
   - Every merge to `main` is published automatically with no manual steps. A failed publish leaves the previous version serving visitors.
   - A public status address reports that the service is alive and which version is running.

3. **Database + first entity.** _Spec:_ [003-database-questions](../../specs/003-database-questions/spec.md)
   - The application keeps its data in a database that survives restarts and redeploys.
   - The first product entity is the **question**: question text (up to 1,000 characters) and a reference answer (up to 5,000 characters), both required. Questions can be created, read, updated and deleted inside the application, but not yet through the website.
   - The home page lists at least five sample questions, read-only. Reference answers are never shown publicly.
   - The home page shows a database status line: the database kind, the schema version and a boot count that goes up with every application start, which proves that data persists.
   - If the database is briefly unreachable, the home page still opens and shows "data temporarily unavailable".

4. **Email code authentication.** _Spec:_ [004-email-otp-auth](../../specs/004-email-otp-auth/spec.md)
   - People sign in with their email address and a one-time code sent to it. There are no passwords, no sign-in links and no sign-up: only active users already known to the application can sign in.
   - In this milestone the only users are site administrators. Operations owns their list in the deployment configuration; the website can never grant or revoke administrator rights. An address removed from the list is deactivated and signed out everywhere. Users are never deleted.
   - A code has 6 digits, is valid for 20 minutes and works once. A new code replaces the previous one. A code allows 5 wrong attempts, and code requests are limited to 5 per email address and 20 per client per hour.
   - Sign-in behaves the same for registered and unregistered addresses, so it never reveals whether an address belongs to a user. Email addresses are not written to logs.
   - Every page, including the home page, requires sign-in. Only the sign-in and sign-out steps, the status address and static files are public. An anonymous visitor is sent to sign in and then returned to the page they asked for.
   - A session lasts 14 days from sign-in; activity does not extend it. The header shows the signed-in email and a **Log out** button.
   - There is no way to bypass the emailed code.

5. **Roles and authorization.** _Spec:_ [005-roles-authorization](../../specs/005-roles-authorization/spec.md)
   - Three roles: administrator, teacher and student. Operations sets three lists of email addresses in the deployment configuration, one per role. One person can be on several lists and so hold several roles. A person on no list cannot sign in. The teacher and student lists are temporary; milestones 8 and 9 replace them with management in the application.
   - Removing any role from a person signs them out everywhere; adding a role does not.
   - A signed-in person always acts in one role. A person with one role gets it right after sign-in. A person with several roles chooses one (in the order administrator, teacher, student) and then lands on the page they originally asked for; until then no other page opens.
   - A person with several roles can switch role from the header at any time without signing out, and lands on the home page.
   - Access follows the current role only: someone who is both an administrator and a student cannot open administrator pages while using the student role. A page the current role may not open shows "access denied", naming the current role; the role is never switched automatically.
   - Every page states which roles may open it, and access is denied by default.
   - Pages: the home page for all roles, with links to only the pages the current role can open; placeholder **Administrator area**, **Teacher area** and **Student area** pages, each for its own role; a placeholder **Staff area** for administrators and teachers.
   - The header shows "Student Competitions · <Role>" in the top left corner, and the email, the role switch (for several roles) and **Log out** on the right.

6. **Administrator area and subjects.** _Spec:_ [006-admin-area](../../specs/006-admin-area/spec.md)
   - The administrator page becomes an administrator area with three tabs: **Teachers**, **Educational institutions** and **Subjects**. Each tab is an ordinary link to its own page (`/admin/teachers`, `/admin/institutions`, `/admin/subjects`), so it can be bookmarked and reloaded. The current tab is highlighted, and `/admin` opens the **Teachers** tab. The area is open only to the administrator role.
   - The **Teachers** and **Educational institutions** tabs are placeholders in this milestone.
   - A **subject** is a knowledge area in which competitions are held, such as mathematics or physics. The **Subjects** tab lists all subjects, active and deactivated, sorted by name ignoring case, with deactivated ones marked. An empty list shows "No subjects yet". The list starts empty.
   - **Create** and **Rename** use a form with one field, the name: trimmed, 1–200 characters, no control characters, and unique ignoring case, including deactivated subjects and non-Latin letters. An invalid or duplicate name shows the form again with the error and the entered value. A change of case alone is a valid rename.
   - **Deactivate** keeps the subject but stops offering it for new questions (milestone 11) and new competitions (milestone 12). Questions and competitions that already use it stay valid. **Activate** reverses it.
   - **Delete** asks for confirmation and is refused while anything uses the subject, suggesting deactivation instead.

7. **Administrator area: educational institutions.** _Spec:_ [007-region-and-institutions-management](../../specs/007-region-and-institutions-management/spec.md)
   - The **Educational institutions** tab shows two lists side by side: regions on the left and the educational institutions of the selected region on the right. On narrow screens they stack, regions first.
   - The selected region is highlighted and kept in the page address, so it survives reloads and bookmarks. With no region selected, the right side shows "Select a region". After an action, the affected region stays selected.
   - Both lists show active and deactivated items, sorted by name ignoring case, with deactivated items marked. Empty lists show "No regions yet" and "No educational institutions yet". There is no preset list; both start empty.
   - Names of regions and institutions follow the same rules as subject names. Region names are unique. Institution names are unique within their region ("already exists in this region"); the same name may exist in different regions.
   - **Regions** offer **Create**, **Rename**, **Deactivate** / **Activate** and **Delete**. Delete asks for confirmation and is refused while the region holds any institution. A deactivated region accepts no new institutions, and none of its institutions can be selected anywhere; the institutions' own statuses do not change, and they stay fully manageable.
   - **Educational institutions** offer the same actions. An institution is created in the selected region, which must be active, and can never move to another region. Delete asks for confirmation, naming the institution and its region, and is refused while anything uses the institution (teacher links from milestone 8, students from milestone 9), suggesting deactivation instead.
   - An institution can be selected (when inviting or editing teachers in milestone 8 and students in milestone 9) only when it and its region are both active. Existing links to an institution that later becomes unavailable stay valid.

8. **User management with consent: teachers.** _Spec:_ [008-teacher-management-consent](../../specs/008-teacher-management-consent/spec.md)
   - Administrators invite teachers by email. Nothing about an invited person is stored until they press **I agree** on the consent page: the whole invitation travels encrypted and tamper-proof inside the emailed link, valid for 7 days. Invitations are rate-limited per inviter and per address. Accepting creates, extends or reactivates the person, stores the names and teacher details and a consent record (role, consent text version, time, inviter), and leads to the sign-in page with the email filled in.
   - An invitation is refused when it was tampered with, expired, its inviter is no longer an administrator, one of its institutions is no longer selectable, or the teacher role was removed or consent withdrawn after it was issued. Expiry has its own message; every other refusal shares one neutral message.
   - Each teacher is linked to one or more educational institutions with **Read** or **Write** access and has one **Can create competitions** setting. Only administrators set them; they are stored and shown, and later milestones enforce them. Only active institutions in active regions can be picked; a link to an institution deactivated later is kept and shown as deactivated. An institution linked to a teacher cannot be deleted.
   - The **Teachers** tab lists current teachers sorted by last name, with email, institutions and access levels, the setting and the date of consent. Each teacher's page edits the names, institutions, levels and setting, or removes the teacher, which signs them out everywhere and deactivates them if no role is left. The email cannot be edited.
   - Every signed-in person has a read-only profile (the header email links to it) with their data, roles, teacher details and the consent texts they accepted. **Withdraw consent** erases the names, replaces the email (administrators keep theirs), removes the teacher role and signs the person out everywhere; consent records are kept.
   - **Delete my data** on the sign-in page emails a one-hour, one-use link that erases the same way, without signing in. Every address gets the same answer.
   - Consent texts are versioned per invitable role and never change once published. The invitation, acceptance, profile and withdrawal flow is shared by every invitable role, so milestone 9 adds students without changing it.
   - `TEACHER_EMAILS` and `STUDENT_EMAILS` are retired: roles they granted were removed once, at deploy. `ADMIN_EMAILS` manages only the administrator role. Emailed links use `PUBLIC_BASE_URL`. No log line contains an email, a name or a link token.

9. **User management with consent: classes and students.** _Spec:_ [009-classes-students-management](../../specs/009-classes-students-management/spec.md)
   - The teacher page is a teacher area like the administrator area, with two tabs: **Students** (opened by `/teacher`) and **Competitions**, a placeholder for milestones 12 and 15.
   - On **Students**, three lists in a row (**Region**, **Educational institution**, **Class**; stacked on narrow screens) choose a class among the available institutions the teacher is linked to, each marked "Read" or "Write". The selection is kept in the page address, and a message says what to choose next.
   - A class belongs to one institution and has a name (unique ignoring case within the institution) and a year of study from 1 to 12. With Write access a teacher creates, edits, deactivates (after a confirmation), activates and deletes classes; a class with a student cannot be deleted.
   - Teachers with Write access invite students one by one into an active class, through the milestone 8 consent flow. Nothing is stored until the student presses **I agree**; only then are the student role and the enrolment (institution and class) stored. An address that already belongs to a student is refused without naming their class, and student invitations are limited to 100 per teacher per hour.
   - A student acceptance is refused when the inviter no longer has Write access to the institution or the class is no longer available, besides the milestone 8 checks. A person who already is a teacher or a student keeps their names when accepting any invitation, teacher invitations included.
   - A class lists its students by last name. **Edit** changes the names or moves the student to another active class of the same institution, with no new consent; **Remove** takes the student role away, signs the student out everywhere and deactivates them if no role is left. Read access shows the same classes and students with no actions, and anything out of reach shows "access denied", also through the page address.
   - Regions, institutions and classes form a chain. Deactivating any of them signs out and hides every student below it until it is activated again, without changing any other status; a blocked student cannot sign in with the student role but can still delete their data. The administrator confirms deactivating a region or an institution.
   - An institution with an enrolled student cannot be deleted; its empty classes are deleted with it. A student's profile shows the institution, the class and the year of study; withdrawal and **Delete my data** erase the enrolment with the rest.

10. **Professional design system and UI guidelines.** _Spec:_ [010-design-system-ui-guidelines](../../specs/010-design-system-ui-guidelines/spec.md)
   - The application has a visual identity: the "Student Competitions" wordmark with an amber logo mark (also the favicon), the Classroom blue palette, Open Sans served by the application itself, an 8 px spacing grid and one type scale, all defined once as design tokens. The look was approved from a mockup before any page changed.
   - Every page shares one frame: a top bar with the logo, the product name and the current role, a user menu (profile link, role switch, theme switch, **Log out**) that opens without JavaScript and folds to an icon on a phone, the area tabs, one content width and a quiet footer.
   - Every existing page is rebuilt from a library of shared components (buttons in three kinds, cards, data tables that become labelled cards on a phone, status badges, notices, empty states with a hint, form fields with an error summary, confirmations, details lists and selectors) with no change in addresses, fields, messages or access. Every page below an area's main page has a back link; every form error is shown beside its field and in a summary headed "There is a problem".
   - The home page greets the person and shows one card per area their role can open, with what is done there; the database line moves to the footer.
   - **Light**, **Dark** or **Device** (the default) is chosen in the user menu or on the sign-in page and kept in that browser only; the server renders every page in the chosen theme.
   - Administrators see every component in every variant at `/admin/components`, outside production only. The binding UI guidelines are in [ui-guidelines.md](ui-guidelines.md); an automated check keeps every page on the tokens and the components.

10.1. **Feedback while a page loads, and a frame that stays in view.** _Spec:_ [010.1-loading-feedback-pinned-frame](../../specs/010.1-loading-feedback-pinned-frame/spec.md)
   - When a link to another page of the application is followed or a form is sent and the next page takes longer than 200 ms, a thin bar in the primary colour runs just under the frame until it arrives. Fast pages show nothing, and nothing starts for a new tab or window, another site, a `#` link or a form the browser refuses. With reduced motion the bar stands still.
   - The button that sent a form shows a spinner and the form cannot be sent again until the next page arrives; the button is never disabled, so the role and theme switches still send their value. A list that submits itself may send a newer choice. A page restored with Back or Forward shows no leftover bar or busy button.
   - On a screen at least 600 px tall the top bar and the area tabs stay at the top while the page still scrolls as a whole; shorter screens and print keep the old flow. Skip-link and error-summary targets and keyboard focus always land below the frame (WCAG 2.2, 2.4.11), without JavaScript; the user menu scrolls inside itself. On a phone the area tabs are 44 px tall.
   - Both come from one small script loaded by the base layout, with no build step and no new dependency; without JavaScript, links and forms work as before. The loading bar and the busy button are in the component library, `/admin/components` and the UI guidelines. Their browser behaviour was checked by hand and with ad hoc Playwright runs, a recorded deviation from automated tests until milestone 16.

11. **Question bank (teacher).** _Spec:_ [011-question-bank](../../specs/011-question-bank/spec.md)
   - The teacher area has a third tab, **Questions** (`/teacher/questions`), between **Students** and **Competitions**. A list of the active subjects chooses the subject (a single active subject is chosen automatically); the subject and the page are kept in the address. Its questions are shown newest first, 10 per page, each in full in one box with its number, its text and its reference answer, with page navigation above and below ("Questions 31–40 of 200", **Previous**, the pages with gaps, **Next**).
   - Every teacher reads the shared bank. Only a teacher with **Can manage competitions** (the milestone 8 setting **Can create competitions**, renamed everywhere with every value kept; old invitations still carry theirs) adds, edits and deletes any question. Both texts are required, trimmed and at most 2,000 characters; duplicates are allowed; a question's subject never changes. **Save question** returns to the first page, **Save and add one more question** opens an empty form with a notice, and editing, Cancel and deleting return to the page the teacher came from, at the question.
   - Deletion is soft: after a confirmation that names the question by its number, it is hidden for good but stays stored unchanged, and can never join a new competition. Any question, deleted ones included, makes its subject undeletable; deactivating the subject hides its questions until it is activated again.
   - The server checks everything: administrators and students get "access denied", and so does every add, edit or delete page and action for a teacher without the setting, checked before any id; an unknown or deactivated subject, and an unknown, deleted or hidden question, are "not found".
   - The milestone 3 sample questions are deleted by the migration and the home page lists no questions; its database line and unavailable message stay, and the teacher card mentions the question bank.
   - Page navigation, a second save button in `form_actions`, a multi-line field and the text card are new components, in the library, `/admin/components` and the UI guidelines first; without JavaScript every chained list now shows a **Show** button. The three-tab row was measured at 360 px and 375 px: one row, under the pinned-frame clearance.

11.1. **Teams (teacher).** _Spec:_ [011.1-teacher-teams](../../specs/011.1-teacher-teams/spec.md)
   - The teacher area has a fourth tab, **Teams** (`/teacher/teams`), between **Students** and **Questions**. It works like **Students**: three lists (Region, Educational institution, Team) choose a team, kept in the address, and the region and the institution stay selected after every action, Cancel and back link. The selected team lists its active members by last name, each with their class. On a phone the four tabs take two rows, measured at 360 px and 375 px under the pinned-frame clearance, which is unchanged; the home page's teacher card names students, teams, the question bank and competitions.
   - A team belongs to one institution for ever and has only a name, unique ignoring case across every institution ("A team named “…” already exists" never says where). With Write access a teacher creates, renames and deletes teams and adds and removes members; with Read access the same teams and members show with no actions. **Add students** lists the active classes of the institution and each student with **Add** or "In this team"; a notice names the student after an addition.
   - A student may be in several teams of their institution, once each; a team holds at most 50 members, blocked ones included, under concurrency too. Adding and removing never change a student's class, role or sessions. A member whose class, institution or region is deactivated is hidden and not counted on the delete confirmation until everything above them is active again.
   - Deletion is soft: the team and every membership stay stored, it is never listed or changed again, and its name is free again. An institution that ever held a team cannot be deleted.
   - Team memberships are personal data: the profile lists them, a deleted team marked "(deleted)", and removal, withdrawal and data deletion erase them, in deleted teams too. The student consent text version 1 was rewritten in place to say so, a one-time exception fenced by the pinned-text test.
   - The server checks everything: administrators and students get "access denied" on all 11 endpoints; Read access, unknown, deleted and unreachable teams, and blocked or other-institution students get it on every management page and action, before anything named is read, and again under lock. No log line or address carries a name.
   - The section heading with actions, hand-built on **Students** until now, is the `section_heading` component, and "In this team" is the new `row_note`; both are in the library, `/admin/components` and the UI guidelines first, and **Students** renders exactly the same markup, pinned by a test.

## Upcoming

12. **Dummy milestone 12.**

12.1. **Creating competitions (teacher).** The **Competitions** tab of the teacher area (`/teacher/competitions`), a placeholder since milestone 9, lists the competitions of a subject and lets a teacher with **Can manage competitions** create and edit them. A competition in this milestone has only a subject, a name and a start date and time; questions, teams, stopping and cancelling come in later 12.x milestones.
    _Choosing a subject:_ exactly as on the **Questions** tab (milestone 11): a drop-down list of the active subjects, sorted by name ignoring case, chooses the subject, and a single active subject is chosen automatically. Until a subject is chosen the page shows "Select a subject to see its competitions"; with no active subject at all it shows the same empty state as **Questions** does. Without JavaScript the list has a **Show** button. The subject is kept in the page address, and an unknown or deactivated subject in the address shows "not found".
    _Competitions:_ a competition belongs to one subject for ever; its subject never changes. Its name is trimmed, 1–200 characters long, has no control characters, and is unique ignoring case within its subject among the competitions that are not **Finished**, under concurrency too ("A competition named “…” already exists in this subject"). The same name may be used in different subjects at the same time. Once a competition is **Finished** its name is free to use again, while the finished competition keeps it; since nothing can finish yet, in this milestone every name is unique within its subject. Saving a competition with its own name, or with only its case changed, is valid. Its start is a date and a time to the minute, and must be later than the moment the form is saved, both when creating and when editing. There is no duration: a competition runs until it is stopped, which a later 12.x milestone adds.
    _Statuses:_ a competition is **Upcoming**, **In process**, **Finished** or **Canceled**. It is **Upcoming** until its start and becomes **In process** at its start on its own, with nobody acting. **Finished** (after a teacher with **Can manage competitions** stops it) and **Canceled** (after a teacher with **Can manage competitions** cancels it) cannot be reached yet; later 12.x milestones add the actions that lead to them. Each status is shown as a badge.
    _List:_ the competitions of the chosen subject are shown in a data table (labelled cards on a phone) with the name, the start and the status badge; there is no column naming who created it. A status filter above the list offers **All** (the default), **Upcoming**, **In process**, **Finished** and **Canceled**, and is kept in the page address with the subject and the page. **Upcoming** lists the soonest start first; every other filter lists the latest start first, and competitions with the same start are ordered by name ignoring case. The list has 10 competitions per page with the page navigation of **Questions** above and below ("Competitions 11–20 of 35"). A subject with no competitions shows "No competitions yet", with a hint that depends on the setting; a filter that matches nothing shows "No competitions with this status".
    _Time zones:_ starts are stored in UTC. A teacher enters the start date and time in their own time zone, as their browser reports it, and every teacher sees every start in their own browser's time zone, in the list and in the edit form. Without JavaScript the form says that the time is entered in UTC and the list shows starts in UTC marked "UTC". A local time that does not exist (skipped by a daylight-saving change) is refused with a message; a local time that happens twice is taken as the earlier one.
    _Creating:_ with **Can manage competitions**, a chosen subject shows **New competition** beside the page heading. It opens a form page with a back link, naming the subject and holding three fields: name, start date and start time. **Save** creates the competition in the chosen subject and returns to its list (filter **All**, first page) with a notice naming the competition; **Cancel** returns to the page the teacher came from. An invalid name, a missing or invalid date or time, or a start that is not in the future shows the form again with the errors and the entered values.
    _Row actions:_ each row has an actions menu, a button that opens a short list of the actions for that competition. In this milestone the only action is **Edit**, offered with **Can manage competitions** on **Upcoming** competitions; a row with no action available shows no menu button, so a teacher without the setting sees no menus at all. The menu is built to take more actions in later 12.x milestones without changing its look or behaviour.
    _Editing:_ **Edit** opens the creation form filled with the current name, start date and start time; the subject is shown but cannot be changed. **Save** keeps the same rules as creating and returns to the page the teacher came from (same subject, filter and page), at the competition, with a notice; so does **Cancel**. A competition that has left **Upcoming** cannot be edited: opening its edit page or saving it, for example after it started while the form was open, shows a refusal saying it has already started, with a link back to the list.
    _Access:_ every teacher sees the competitions of every active subject, whoever created them. Creating and editing need **Can manage competitions**, and any teacher with it can edit any upcoming competition. Administrators and students get "access denied" on every page and action of the tab, also through the page address or a submitted form. A teacher without the setting gets "access denied" on the create and edit pages and actions, checked before any id or subject is read. An unknown competition, a competition of a deactivated subject, or a competition that does not belong to the subject in the address shows "not found". Every change is a form submission with the cross-site request check, and no log line contains an email, a name or a competition name. A subject used by any competition cannot be deleted (milestone 6), and deactivating it hides its competitions until it is activated again.
    _Components:_ the pages are built from the existing components (selectors, data tables, page navigation, notices, empty states with a hint, form fields with an error summary, refusals, back links). The actions menu (a `<details>` element like the user menu, so it opens without JavaScript, with 44 px entries that stay reachable on a phone card and by keyboard), the date and time fields, the competition status badge and the local-time display are new: each is added to the component library, `/admin/components` and the UI guidelines first, and only then used. The local-time conversion lives in the existing application script, with no new dependency.
    _Out of scope:_ duration, questions and teams in a competition, stopping, cancelling and deleting a competition, edit rights per competition, and the student's view (milestone 13).
    _Test:_ a teacher with **Can manage competitions** creates a competition in the chosen subject and finds it in the list as **Upcoming**, with its start shown in their time zone and stored in UTC; edits its name and start; and is refused a start in the past or now, an empty name, a name of 201 characters, and the name of another competition of the same subject, in any case, while the same name is accepted in another subject. A start that passes turns the competition into **In process**, after which its row has no menu and its edit page and edit action show the refusal. The status filter shows only matching competitions and is kept across pages, with 10 competitions per page. A teacher without the setting sees the list with no **New competition** and no menus, and gets "access denied" on the create and edit pages and actions; administrators and students get "access denied" on every page and action. A competition of a deactivated subject shows "not found", and a subject with a competition cannot be deleted.

15. **Best answer selection + results.** For each question, the best answer is selected from the group's answers; competition results are saved and displayed.

    _Test:_ the best answer is determined, the results page works. The results still show a question deleted after the competition, a subject deactivated after it and a team deleted after it. A teacher with Read access sees the results of that institution's students and none from institutions they are not linked to.
